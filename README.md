# STM32 Guitar Tuner

A real-time embedded guitar tuner written in C for the STM32F767ZI. The firmware uses timer-triggered ADC sampling, circular DMA acquisition, and a custom YIN pitch detector to estimate the fundamental frequency of a guitar signal and display tuning error across a 19-position LED indicator.

The project is software-focused. It emphasizes deterministic data acquisition, embedded DSP, modular C design, runtime debugging, and hardware-aware performance tuning without relying on a prebuilt tuner or DSP framework.

## Project Status

Active development. The following functionality is working:

- Deterministic 20 kHz ADC sampling
- Circular DMA acquisition with half-transfer and transfer-complete processing
- Custom YIN pitch detection in C
- Confidence and signal-level gating
- Frequency-to-cents conversion
- 19-position LED tuning indication
- UART diagnostics through PuTTY
- Optional Python waveform capture and offline visualization

Current work includes automatic open-string selection, display stabilization, pitch-tracking hysteresis, and further profiling of the DSP path.

## Key Features

- STM32F767ZI Cortex-M7 running at 216 MHz
- Hardware-timed ADC conversions generated by TIM2 TRGO
- ADC1 acquisition through circular DMA with no per-sample CPU polling
- 4,096-sample DMA buffer divided into two 2,048-sample processing windows
- Custom YIN fundamental-frequency estimator
- Cumulative mean normalized difference function (CMNDF)
- DC-bias removal and amplitude-based silence rejection
- Confidence-gated pitch results
- Standard guitar tuning targets and cents-based pitch error
- 19-position LED display for flat, in-tune, and sharp indication
- Source-level debugging with SEGGER Ozone and J-Link

## Module Breakdown

main.c - Application startup, system-clock configuration, DMA-buffer ownership, acquisition-event handling, pitch-result coordination, and high-level LED behavior.

IO_init.c - STM32 peripheral initialization for GPIO, UART, ADC, DMA, TIM2, and related HAL handles.

yin_tuner.c - Signal preprocessing, YIN difference function, CMNDF, threshold selection, interpolation, frequency estimation, and confidence calculation.

led_display.c - Physical LED table, GPIO output control, all-off behavior, and cents-to-position mapping.

stm32f7xx_it.c - Interrupt entry points required by the STM32 HAL integration.

## Acquisition and Processing Flow

Analog guitar signal

MCP6002 input conditioning and mid-supply bias

TIM2 update event at 20 kHz

TIM2 TRGO hardware trigger

ADC1 conversion

DMA transfer into the circular sample buffer

Half-transfer or transfer-complete notification

2,048-sample YIN analysis window

Frequency and confidence result

Nearest open-string target

Cents deviation

19-position LED indication

The hardware sampling path is:

TIM2, TRGO, ADC1, DMA, RAM

The CPU is notified only when a complete processing block is available. The DMA callbacks set readiness flags, while the YIN calculation runs outside interrupt context.

## Deterministic ADC Acquisition

The ADC is not started from a software polling loop. TIM2 generates a hardware trigger at a fixed rate, and ADC1 begins one conversion for each trigger. DMA copies each conversion result directly from the ADC data register into RAM.

This provides:

- Uniform sample spacing
- Minimal sampling jitter
- No CPU involvement for each individual ADC sample
- Continuous acquisition while the previous buffer half is processed
- A clear producer-consumer boundary between DMA and the pitch detector

## Current Clock and Timer Configuration

Current clock values:

SYSCLK: 216 MHz

HCLK: 216 MHz

PCLK1: 54 MHz

TIM2 clock: 108 MHz

ADC sample rate: 20 kHz

TIM2 preserves the 20 kHz sample rate using:

TIM2 update rate = TIM2CLK / ((PSC + 1) x (ARR + 1))

TIM2 update rate = 108,000,000 / (54 x 100)

TIM2 update rate = 20,000 Hz

Current timer values:

htim2.Init.Prescaler = 53;

htim2.Init.Period = 99;

The timer update event is exported as TIM_TRGO_UPDATE. ADC1 uses ADC_EXTERNALTRIGCONV_T2_TRGO as its external conversion trigger.

## DMA Buffer Model

DMA_HALF_SAMPLES is 2,048 samples.

DMA_TOTAL_SAMPLES is 4,096 samples.

adc_dma_buf holds 4,096 uint16_t samples.

The circular buffer is divided into two regions:

adc_dma_buf[0 through 2047] - first half

adc_dma_buf[2048 through 4095] - second half

At 20 kHz:

One sample: 50 microseconds

One 2,048-sample half: 102.4 ms

One 4,096-sample full buffer: 204.8 ms

Each sample occupies two bytes, so the DMA buffer uses 8,192 bytes of RAM.

The half-transfer callback marks the first 2,048 samples ready while DMA continues filling the second half. The transfer-complete callback marks the second half ready, after which circular DMA wraps to the beginning of the buffer.

The lowest standard guitar string is E2 at approximately 82.41 Hz. At a 20 kHz sample rate:

Samples per E2 period = 20,000 / 82.41 = approximately 242.7 samples

Cycles in one 2,048-sample window = 2,048 / 242.7 = approximately 8.4 cycles

This provides several full periods of the lowest supported note while keeping the update interval practical.

## YIN Pitch Detection

The project implements YIN directly in C rather than using an external DSP library.

Processing stages:

1. Validate the analysis-window size.
2. Remove the measured DC bias from the ADC samples.
3. Reject low-amplitude input before attempting pitch detection.
4. Compute the YIN difference function over the supported lag range.
5. Compute the cumulative mean normalized difference function.
6. Find the first threshold crossing and continue to the local minimum.
7. Refine the integer lag with parabolic interpolation.
8. Convert the refined period from samples to hertz.
9. Return frequency, confidence, and validity to the application layer.

The central relationship is:

frequency = sample_rate / period_in_samples

Expected periods at 20 kHz:

E2, 82.41 Hz: approximately 243 samples

A2, 110.00 Hz: approximately 182 samples

D3, 146.83 Hz: approximately 136 samples

G3, 196.00 Hz: approximately 102 samples

B3, 246.94 Hz: approximately 81 samples

E4, 329.63 Hz: approximately 61 samples

## Result Interface

The pitch detector returns:

freq_hz - Detected frequency in hertz

confidence - YIN confidence value

valid - Indicates whether the result passed signal-level and pitch-validity checks

Musical interpretation is kept outside the YIN module. The application layer selects the supported string target, calculates cents relative to that target, and maps the result to the LED display.

This keeps the YIN implementation reusable for signals beyond standard guitar tuning.

## Standard Tuning and LED Mapping

Supported open-string targets:

Low E / E2: 82.41 Hz

A / A2: 110.00 Hz

D / D3: 146.83 Hz

G / G3: 196.00 Hz

B / B3: 246.94 Hz

High E / E4: 329.63 Hz

Pitch error is calculated in cents:

cents = 1200.0f x log2f(measured_hz / target_hz)

Negative cents indicate flat pitch. Values near zero indicate in tune. Positive cents indicate sharp pitch.

The 19-position display uses one active LED at a time. The center green LED represents the in-tune region. Nearby green and yellow LEDs indicate smaller errors, while the outer red LEDs indicate larger errors. The physical LED order is stored in a GPIO lookup table in led_display.c.

When input amplitude or YIN confidence falls below the configured threshold, the display is blanked rather than showing stale or misleading tuning information.

## Peripheral Interfaces

Guitar input - ADC1 - Samples the conditioned and biased analog guitar waveform.

Sample clock - TIM2 TRGO - Generates deterministic 20 kHz ADC conversion triggers.

Sample transport - DMA - Transfers ADC results into the circular RAM buffer.

Tuning display - GPIO - Drives the 19-position LED array.

Diagnostic output - USART6 - Sends frequency, confidence, cents, and LED-state information to PuTTY.

Debug interface - ST-LINK or J-Link - Supports flashing, breakpoints, watch expressions, memory inspection, and profiling.

## Debugging and Instrumentation

The project supports source-level debugging through SEGGER Ozone and J-Link.

Typical debugging workflow:

1. Build the ELF with debug symbols.
2. Load the ELF in Ozone.
3. Set breakpoints in the DMA-event processing path or YIN stages.
4. Inspect freq_hz, confidence, lag values, LED indices, and DMA samples.
5. Use global volatile diagnostic variables when a value must remain visible outside an optimized local scope.

UART output is available for runtime validation. Example:

freq=82.23 Hz cents=-3.59 LED=P9

The Python utilities are optional development tools and are not required by the deployed tuner firmware. The waveform plotting scripts were adapted from online examples and modified to decode and display the project's ADC stream.

## Build and Flash

### Prerequisites

- VS Code
- CMake
- Ninja
- ARM GNU Toolchain, including arm-none-eabi-gcc
- STM32Cube tools or an equivalent STM32 HAL and CMSIS installation
- SEGGER Ozone and J-Link, or ST-LINK-compatible flashing tools

### Verify the ARM Toolchain on Windows

Get-ChildItem "C:\ST" -Recurse -Filter arm-none-eabi-gcc.exe -ErrorAction SilentlyContinue

Get-ChildItem "C:\Program Files" -Recurse -Filter arm-none-eabi-gcc.exe -ErrorAction SilentlyContinue

Get-ChildItem "C:\Program Files (x86)" -Recurse -Filter arm-none-eabi-gcc.exe -ErrorAction SilentlyContinue

Add the toolchain directory to the current PowerShell session if required:

$env:Path += ";C:\path\to\arm-gnu-toolchain\bin"

arm-none-eabi-gcc --version

### Configure and Build

This repository uses CMake presets.

cmake --preset stm32-debug

cmake --build --preset stm32-debug

For subsequent incremental builds:

cmake --build build

### Clean Rebuild

Remove-Item -Recurse -Force .\build

cmake --preset stm32-debug

cmake --build --preset stm32-debug -v

The generated ELF can be loaded directly into Ozone for flashing and source-level debugging.
